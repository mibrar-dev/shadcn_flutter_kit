## Per component

### 1. skeleton — 484 → 443 LOC

- Widgets-only shimmer (`RepeatedAnimationBuilder` + a gradient `Container`).
- Dropped the `package:skeletonizer` dependency (banned by the re-architecture)
  and the `avatar` dependency: the old `asSkeleton(type: SkeletonType.avatar)`
  only picked a skeletonizer avatar mode, which is not a thing without it.
  `deps.components` is therefore empty.
- Deleted `Snapshot`, `enableSwitchAnimation` (a knob nothing read) and the
  second, conflicting pair of colour defaults (`SkeletonThemeDefaults` said
  `0x0D171717`/`0x1A171717` where the config layer said `primary@5%`/`@10%`).
- `snapshot` recomputed `enabled = !snapshot.hasData` *after* reading the
  argument, so `enabled: false` could still paint.

### 2. carousel — 1,537 → 962 LOC

- `CarouselTransition` enum + one exhaustive `switch`; `CarouselSizeConstraint`
  subclasses collapse to `itemExtent` / `viewportFraction`.
- `CarouselController` and the pure layout maths (`carouselVisibleRange`,
  `carouselPageAt`, `carouselPageVisible`, `carouselStepTarget`,
  `carouselSnapTarget`) live in `carousel_style.dart` to fit the 400-line cap.
- `CarouselIndicator` deleted: it was a pass-through over `DotIndicator`.
  `deps.components` is empty even though the batch data lists `dot_indicator`.
- `wrap`, `draggable` and `pauseOnHover` became theme-only rows — the widget
  arguments were never read in a way a caller could observe.
- The theme is resolved in `build()`, not `didChangeDependencies()`: a plain
  widget update does not schedule a dependency change, so the app leg was
  applied one frame late (and never, for a `setState` in the parent).

### 3. tooltip — 1,009 → 620 LOC

- `Tooltip` now auto-wraps bare content in `TooltipContainer`, so callers
  return their content unchanged.
- Deleted `InstantTooltip` (a duplicate of `Tooltip` with a zero delay) and
  `FixedTooltipOverlayHandler`.
- Dropped `adaptiveOverlay`: overlay placement belongs to
  `overlay_configuration` (B12).
- `TooltipOverlayHandler` survives as an adapter that routes to
  `OverlayManager.showTooltip`, so `ShadcnLayer.tooltipHandler` keeps working.

### 4. input_otp — 1,381 → 718 LOC

- One hidden `EditableText` driven through `EditableTextHost` replaces the
  per-slot controller/focus-node/`GlobalKey` design, so typing, pasting, the
  caret and undo are the framework's. The value is a `String`, not
  `List<int?>` of UTF-16 code units, so a surrogate pair stops occupying two
  slots.
- The whole `InputOTPChild` factory DSL (`input`, `character`, `separator`,
  `space`, `empty`) is gone, replaced by `length`, `filter`, `keyboardType`
  and `separator` + `separatorEvery`. `InputOTPChildData` — a public class
  exposing the private `_InputOTPState` — is deleted.
- Validation moved onto the shared `EditableTextValidation` primitive, so
  `autovalidateMode` is live for all three modes (`initial` on mount,
  `changed` per edit, `submitted` on submit) instead of being compared in
  `didUpdateWidget` and never acted on.

Four bugs found while porting (all covered by tests):

1. Wiring both `EditableText.onChanged` *and* the host's controller listener
   fired every callback twice per edit.
2. The controller listener also fires for a selection-only change (focusing
   the field selects offset 0), so `onChanged` reported an empty code right
   after mounting. The reported text is now compared against the last one.
3. `_clampCode` truncated before filtering, so `1a2b3` in a 4-slot field lost
   the valid `3`. Filtering now runs first.
4. An `initial` validator that arrived after mount never ran, because
   `EditableTextValidation.onChanged` only fires in `changed` mode.

### 5. text_area — 312 → 269 LOC

- A 30-field wrapper over `Input` with three-line defaults, a multiline
  keyboard and `sentences` capitalisation (a text area is prose; `Input`
  defaults to `none` for codes).
- **No theme class.** Every visual row is `InputTheme`'s, and the widget leg
  is forwarded verbatim; a second class would duplicate ten rows and let the
  two drift. `meta.json` records `theme: null` with the reason, and
  `InputTheme` / `InputSurface` / `resolveInputSurface` are re-exported from
  `text_area.dart` so an app that only uses text areas still gets the type.
- The drag-resize handle is deleted: resizing is a layout decision that
  `minLines` / `maxLines` / `expands` already express, shadcn/ui has no such
  affordance, and the old handle did `onPanUpdate` arithmetic on
  `double.infinity` (`initialWidth` default) whenever `expandableWidth` was
  set. `onHeightChanged` / `onWidthChanged` went with it.
- `isDateEnabled`-style bloat: the old widget forwarded ~80 `TextField`
  parameters, none of which any caller in the registry set.

### 6. calendar — 2,597 → 1,038 LOC (+206 in the primitive)

- One `Calendar` widget drives all three granularities through `viewType`
  (`date` / `month` / `year`) and one shared `_Grid` layout, replacing
  `CalendarGrid`, `MonthCalendar` and `YearCalendar` with their duplicated
  loops.
- `CalendarItemType` had ten cases for six visual rows (four never assigned
  by any caller) behind a 341-line switch that re-read `width ?? scaling * 32`
  in every branch. One cell painter driven by `CalendarValueLookup` + `today`
  replaces it.
- **Value types moved to the primitive.** `CalendarView`, `CalendarValueLookup`
  and the `sealed` `CalendarValue` with its three shapes now live in
  `primitives/date_math.dart`, the batch's named primitive, because
  `date_picker` (B13) and `object_input` (B21) read the same values. The file
  was already 202 lines; the value types were written to fit under the 400-line
  cap with it (397 today), which is why `CalendarValue` exposes three named
  lookups instead of the old defaulted-argument one and has no `toString`.
- The grid maths comes from `monthGrid`, so `firstDayOfWeek` is a parameter
  (the old `CalendarGridData` hard-coded Monday) and cells are built from
  `DateTime(y, m, d + i)` instead of `date.add(Duration(days: i))`, which
  skipped or repeated a day across a DST boundary.

Five bugs found while porting, all covered by tests:

1. `_toggleMulti` seeded its working list with `const <DateTime>[]`, so the
   first tap in multi mode threw `UnsupportedError: Cannot add to an
   unmodifiable list` out of the tap handler.
2. `selectionMode: none` still reported a change: `select()` returned the
   unchanged value and the tap handler forwarded it. A grid is now read-only
   without `onChanged` *and* under `none`.
3. The year grid looped `start..view.year + 11` from a decade start, drawing
   25 cells instead of 16.
4. The month and year grids compared `now` with `isAtSameMomentAs`, so "today"
   never highlighted in either grid. Month and year now compare by month and
   by year.
5. `RangeCalendarValue.toMulti` walked the span day by day: a ten-year range
   allocated 3,650 `DateTime`s inside a tap handler.

Four more found by the keyboard-navigation tests (QA round 2):

6. **An arrow off the grid moved the wrong way.** The focus move resolves an
   index for `ArrowDown`; with no row below, it fell through to the *date*
   branch, which stepped `previousWeek` — so "a week down" from the last row
   silently became "a week earlier". Only a month or year move may leave now.
7. **The focus started on the 1st of the month.** It was resolved in
   `initState`, before the slot list existed, so "the first selectable day" read
   an empty list and returned `view`'s first day. It is resolved from the built
   slots instead.
8. **A month or year cell could hold neither the focus nor "today."** Those
   cells hold the *first* of the month (or of January) and were compared by day,
   so the ring and the today fill never appeared in those two grids. Matching is
   now at the grid's own granularity — this re-broke a bug round 1 had fixed at
   the `today` call site, and fixed it once for both.
9. **The screen reader heard the date twice.** The `Semantics` label said
   "Mar 14, 2024" and the `Text` inside added "14". The painted number is now
   `ExcludeSemantics`-wrapped.

**Not migrated: `DatePickerDialog`** (501 LOC in `_date_picker_dialog_state.dart`
+ 99 in `date_picker_dialog.dart`). It needs the popover and overlay stack that
batch B13 owns, and half a dialog with no anchor is worse than none. B13 builds
`date_picker` on this component (`view:`, `viewType:`, the value types and the
`stateBuilder` hook are all that a picker needs from here).

## Deviations and open questions

1. **DatePickerDialog deferred to B13** — as above. If B13 wants the old dual
   month layout, `Calendar` currently offers one month at a time.
2. **`CalendarTheme` has no `copyWith` or `lerp`, unlike every other theme.**
   Both were dead code here — nothing in the registry calls either, and the
   calendar has no animated theme change — so the "no dead code" rule removed
   them. `==` / `hashCode` read one `_fields` list instead, so a new row cannot be
   added to the constructor and forgotten there. If Studio or the CLI generates
   `copyWith` calls, this is the one theme that will need it back.
3. **`CalendarValue` has no `toString`** — the line budget in `date_math.dart`
   did not allow it. Debug output falls back to the default `Instance of`.
4. **`MultiCalendarValue.toRange` asserts a non-empty list.** A tap in
   `multi` mode never produces an empty value (it reports `null` instead), so
   the assert documents a caller error rather than guarding a reachable path.
5. **`Calendar` cells are `GestureDetector`s, not `Button`s.** The plan lists
   `button` as a dependency, but a day cell needs a fixed square with a
   per-cell radius cap and no padding; going through `Button` added a size
   table fight and a focus node per day for no visual gain. The keyboard layer
   is on the grid instead of on the cells, which is what makes one tab stop
   possible (see above). QA round 1 asked for arrow-key traversal; round 2 asked
   for the full react-day-picker contract, which is now there.
6. **`text_area` ships no `text_area_theme.dart`.** Flagged in `meta.json` as
   `theme: null` with a reason; if Studio expects the file to exist, the CLI
   needs to honour `theme: null`.
7. **`skeleton` has no avatar mode.** Anything that used
   `SkeletonType.avatar` needs a real `avatar` component (batch B14/B15).
