Status: **done** — all four gates green. One residual in item 3 that needs a codegen

## 1. `ShadcnApp` shortcuts/actions merge

### Root cause

`ShadcnApp` forwarded `shortcuts`/`actions` verbatim to `WidgetsApp`:

```dart
shortcuts: shortcuts,   // WidgetsApp: `widget.shortcuts ?? defaultShortcuts`
actions: actions,       // WidgetsApp: `widget.actions ?? {…defaults, ScrollIntent…}`
```

`WidgetsApp` **replaces** its defaults when either map is non-null (verified in
`flutter/lib/src/widgets/app.dart:1820-1829`, and `defaultShortcuts` is a
platform-dependent getter: android/fuchsia/linux/windows vs iOS/macOS). Any app
that supplied a single binding therefore lost, app-wide:

| Key | Intent | Default action |
|---|---|---|
| `Tab` / `Shift+Tab` | `NextFocusIntent` / `PreviousFocusIntent` | `NextFocusAction` / `PreviousFocusAction` |
| `Enter` / `Space` / `numpadEnter` / `select` / `gameButtonA` | `ActivateIntent` | — (bound per control) |
| `Escape` | `DismissIntent` | — (bound by `ModalRoute`) |

`buttons.dart`/`Clickable` (`primitives/clickable_state.dart:177`) and
`ModalRoute` only install the **action**, never the key binding, so the two
paths above really were dead.

### Fix

`lib/registry/components/app/app.dart` — two private getters, applied at the
`WidgetsApp` call site:

```dart
Map<ShortcutActivator, Intent>? get _mergedShortcuts {
  if (shortcuts == null) return null;                       // platform default intact
  return <ShortcutActivator, Intent>{...WidgetsApp.defaultShortcuts, ...?shortcuts};
}

Map<Type, Action<Intent>>? get _mergedActions {
  if (actions == null) return null;
  return <Type, Action<Intent>>{...WidgetsApp.defaultActions, ...?actions};
}
```

Caller entries win (spread last). The explicit `null` passthrough matters: if
the merge ran unconditionally, an app that supplies *neither* map would lose the
framework's `ScrollIntent: Action<ScrollIntent>.overridable(…)` wrapper that
`_WidgetsAppState` adds on top of `defaultActions` — a new silent regression.

Documented in the field docs, the file header ("Old bugs fixed, not ported"
list) and a new **Keyboard shortcuts and actions** README section.

### Regression tests (`test/registry/components/app_test.dart`, 8 new)

Proved by reverting the fix and re-running — **4 of the 8 fail without it**:

| Test | Without the fix |
|---|---|
| `regression: custom shortcuts keep Tab focus traversal` | **FAIL** — `NextFocusIntent lost its Tab binding` |
| `regression: custom shortcuts keep Escape dismissal` | **FAIL** — route cannot be closed |
| `regression: app-level Enter still produces ActivateIntent` | **FAIL** — `Enter lost its ActivateIntent binding` |
| `merges actions over the framework defaults` | **FAIL** — no `NextFocusAction` / `DismissAction` in the tree |

Also added (pass either way, they pin the contract):
`regression: custom shortcuts keep Enter activation` (the brief asked for it — it
passes without the fix because `Clickable` binds Enter locally, so the dedicated
`app-level Enter` test above is the real proof), `a shadcn Dialog still closes on
Escape`, `caller entries win over a default binding` (rebinding `Tab` to a custom
intent suppresses traversal), `no shortcuts/actions keeps the platform defaults`.

**Finding worth recording:** the shadcn `Dialog` installs its *own*
`Shortcuts { Escape → DismissIntent }` + action
(`components/dialog/dialog.dart:346-353`), so it never depended on the app-level
map. The `RawDialogRoute` case is the one that actually regressed, which is why
that variant is the regression-proof.

### Docs workaround removed

`docs/lib/main.dart` no longer spreads `WidgetsApp.defaultShortcuts` /
`defaultActions`; it passes only `docsShortcuts` and the palette action, and the
explaining comment now says the component merges. The docs focus tests
(`docs/test/focus_test.dart`: "TOC links are tab-reachable", "shell Tab order is
header, sidebar, content, TOC") still pass — now relying on the fixed component.

## 2. `primitives/table_layout` — negative sizing budget

### Root cause

`table_layout_sizing.dart` computed the free-space budget as

```dart
double remainingWidth  = constraints.hasBoundedWidth  ? constraints.maxWidth  - fixedWidth  : double.infinity;
double remainingHeight = constraints.hasBoundedHeight ? constraints.maxHeight - fixedHeight : double.infinity;
```

with **no zero clamp**. When the fixed tracks overflow the incoming constraints —
the brief's "narrow constraints, resized columns, zero-width viewport" — the
budget goes negative and reaches two places that cannot accept one:

1. the **"extent" argument of the children's intrinsic queries**
   (`const double extent = rowHeights[row] ?? remainingHeight;` →
   `child.getMaxIntrinsicWidth(extent)`), which the framework asserts on;
2. `TableLayoutResult.remainingWidth` / `remainingHeight`, which are **public**
   accessors fed into `BoxConstraints.tightFor(width: cellWidth, height: cellHeight)`
   in `performLayout`.

Note the loose twin right next to it *was* clamped (`max(0, minWidth - used)`),
so the asymmetry was the tell.

Reproduced in a widget test (an intrinsic row/column next to a fixed one that
overflows the viewport); the framework reports

```
The height argument to getMaxIntrinsicWidth was negative.
The argument to getMaxIntrinsicWidth must not be negative or null.
```

The same negative also comes out of the intrinsic-computer path
(`computeMin/MaxIntrinsicWidth/Height`), so the clamp is applied at **both**
budget computations.

### Fix

- `max(0.0, …)` on the first budget (`maxWidth - fixedWidth`,
  `maxHeight - fixedHeight`) and on the recomputed one
  (`maxWidth - usedColumnWidth`, `maxHeight - usedRowHeight`).
- `max(0.0, …)` around the flex track assignment. Its inputs are non-negative
  after the clamp, but `performLayout` hands them straight to
  `BoxConstraints.tightFor`, so a negative `FlexTableSize.flex` (a caller could
  pass one) would assert exactly the "negative minimum width" error — the
  defensive clamp costs one line and closes that door.
- Documented in the file header.

Behaviour is unchanged for every non-overflowing grid: `min(intrinsic, 0)` and
`min(intrinsic, negative)` both store the same value (`max(existing, …)`), and
the `remainingWidth > 0` guards already skipped the flex budget when it was
negative. Only the child extent and the public accessors change.

### Regression tests

- `test/registry/primitives/table_layout_test.dart`, group **`overflowed sizing
  budget`** (11 tests). Verified by reverting the fix: the intrinsic-row and
  intrinsic-column tests fail with the framework assert above.
- `test/registry/components/table_test.dart`, group **`resized columns in a
  cramped viewport`** (4 tests): the `ShadcnTable` + `ResizableTableController` +
  `ScrollController`s shape from the docs preview, at 200/180/0-viewport widths,
  with frozen cells, plus a real divider drag 900px past the viewport. These are
  guards (the component always emits `FixedTableSize`, so they pass either way).

## 3. `components/formatter` + `components/color` — `meta.json` `api`

### What was actually wrong

Both `api` blocks named only the *classes*, so the components' real entry points
— **`TextInputFormatters`**, a factory set whose ctor is private
(`const TextInputFormatters._()`, so the docs codegen cannot extract a
constructor for it), and `ColorDerivative`'s four **static factories** — were
absent from the metadata. `locale_utils` (`"methods": ["SizeUnitLocale.format"]`)
and `empty_state` (`"methods": ["EmptyStateVariant.icon", …]`) already establish
the convention for naming static members; `docs/lib/generated/docs_api.dart`
documents the resulting picks (`color → ColorDerivative`, `formatter →
TimeFormatter`) as intended.

### Change

`components/formatter/meta.json` — `api` gains
`functions: ["constraintToNewText"]`,
`constants: ["TextInputFormatters.toUpperCase", "TextInputFormatters.toLowerCase"]`
(the two `static const` fields) and
`methods: ["TextInputFormatters.time", ".integerOnly", ".digitsOnly",
".mathExpression", ".hex"]`.

`components/color/meta.json` — `api` gains a 22-entry `methods` list:
`ColorDerivative.fromColor/fromHex/fromHSV/fromHSL` (the primary entry points),
the `changeTo*` edit family, `transform`, `toColor`, `toHSVColor`, `toHSLColor`.

Both READMEs were rewritten to **lead with the real primary entry point** (the
factory set / the static factories), carry an `## API` member table in the
`locale_utils` shape, and explain that the implementation classes are reachable
only through the factories. The manifest schema
(`rearch/reports/registry_manifest.v2.schema.json`) documents these `api` keys as
free-form ("named group of lists"), and the CLI's `checkApi` accepts them, so the
CLI single-owner preflight and `flutter_shadcn info` now see the real surface.

The docs codegen picks the metadata up: `docs_snippets.dart` now renders, for
`formatter`, the whole factory set as the first Usage snippet, and for `color`,
the four static factories.

### Residual (needs a codegen change — out of scope here)

`docs/tool/src/dart_scan.dart` step 4 returns the first `api.classes` candidate
with a **public unnamed constructor**, so:

- `color` API Reference still renders **0 rows** (`ColorDerivative` has only the
  no-arg `const ColorDerivative()` + factory constructors, which
  `_classApiFacts` filters out by name). No metadata can change this: the
  entry file has no other public class.
- `formatter` API Reference still surfaces `TimeFormatter.length`. The codegen
  cannot pick `TextInputFormatters` because its only constructor is named
  (`._()`), and `docs/tool/gen_docs_data_test.dart` pins the current picks
  (lines 193-194, 200) plus `hasApiTable == true` for every component — so
  removing the constructible classes from `api.classes` would break that test
  *and* turn the table into "no constructor API table".

Recommendation for a follow-up: extend `extractApi` to fall back to a
statically-declared entry point (an `api.methods` / `api.statics` group) for
components whose primary surface is a factory set or static factories, and let
`render_api.dart` render a member table instead of only constructor params.
