## Deviations from the brief/plan

1. **Validator is hand-written, not `json_schema`-based.** The brief enumerates
   the checks ("schemaVersion 2, ids, files, deps closure references existing
   ids, sha256 format"); the cross-referential closure and on-disk checks cannot
   be expressed in JSON Schema, and the v2 schema JSON is not guaranteed present
   next to remote manifests. The `json_schema` package remains a dependency for
   the kept generic `SchemaValidator`. The implemented rules mirror
   `registry_manifest.v2.schema.json` exactly (same id/relPath/sha256 regexes,
   same allowed keys per block, `additionalProperties: false` enforced as
   "unknown key" errors).
2. **relPath checks are stricter than the schema regex where the schema
   description demands it**: the schema pattern allows backslashes, but its
   description says "forward slashes, no leading ./ or /" — the validator
   rejects backslashes and `..` segments with dedicated messages.
3. **Extra semantic rules beyond the brief's list** (all from the schema
   descriptions): unit files must live under their layer dir; component
   `files`/`userOwned` must live under `components/<id>/`; `userOwned` must end
   `_theme.dart`; `files` ∩ `userOwned` = ∅; `preview.dart` must not be listed
   in `files`; component `entry` must be `components/<id>/<file>.dart`; preset
   `file` must be `themes/<id>.json`; `fileHashes` must cover every declared
   file (one-directional — extra hash keys are allowed, e.g. the fixture keeps
   a hash for a file not declared); primitive→primitive cycles rejected (plan
   §6.1 "cycles rejected").
4. **Component entries must NOT contain an `id` key** (the schema's component
   object has `additionalProperties: false` and no `id` property — the map key
   is the id). The fixture therefore omits `id`; a component with an `id` key is
   rejected as an unknown key.
5. **Validator split into two files** (`manifest_schema_validator.dart` +
   `manifest_component_checks.dart`) to stay under the ~400-line limit; the
   component-block checks live in a documented-internal helper class called by
   `ManifestSchemaValidator.validate`. Tests were split the same way.
6. **`RegistrySchemaValidationException` was deleted with `registry_model.dart`.**
   Catch-sites remain in `add_command.dart`, `init_command.dart` (both B5) and
   `multi_registry_add_part.dart` — they must switch to the v2 validator's
   `SchemaValidationResult` (or a new exception) when they adapt. B1 keeps no
   compatibility shim (clean break, plan §9).

## Open questions

1. **`schema_source.dart` is now unreferenced** (its only consumers were the
   deleted `ComponentsSchemaValidator` and the old barrel). Kept per plan §5.4
   "adapt". B5's `validate_command`/`commands_doctor` rewrites can either use it
   (e.g. to locate `manifests/registry.schema.json` for display) or it can be
   deleted in a later batch — decision needed.
2. **Where should validation failures surface?** `validate` returns
   `SchemaValidationResult` (isValid + errors). If B5 wants a throwable for the
   `validate` command (like the old `RegistrySchemaValidationException`), that
   exception class needs a new home — suggest defining it next to the validator
   in B5.
3. **Fixture hash values** are `sha256(relPath)` placeholders, not hashes of
   real file contents — the validator checks format/coverage only (hash-vs-disk
   diffing is B3's lock/update job). Flagging in case B7's golden fixture
   expects content-derived hashes.
