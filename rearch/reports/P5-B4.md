## 2. Design notes

- **Closure** (plan §9.7): cycle-tolerant iterative DFS over the primitive graph;
  component edges are BFS. All result lists are sorted, so the plan/lock are
  deterministic. Unknown component/foundation/theme/primitive ids raise
  `ManifestClosureException` with the referencing component.
- **Layout** (plan §3): `targetPathFor` maps `foundation|theme|primitives|components`
  verbatim under `<installRoot>/…`; `themes/*.json` is rejected (build-time input).
- **Import guard** (plan §9.8): a regex line scan of `import`/`export`; `dart:`/`package:`
  are ignored; every relative target is resolved against the file's registry dir and
  must stay under one of the four layer dirs. The whole batch is guarded before any
  file is written, so a bad import aborts the install atomically.
- **User-owned** (plan §1.5, §4): `<name>_theme.dart` is written only when absent;
  an existing one is `keep`ed and its install-time hash is recorded. `update`/`add`
  never overwrite it.
- **Hash skip**: a destination whose bytes equal the source is `skip`/`identical`;
  a differing registry-owned destination is `skip`/`locally modified` unless the caller
  passes `overwrite: true` (which `add` defaults to false — `update` is B5's job).
- **Lock v2**: `InstallLockBuilder` emits a delta (registry info + layer units/files +
  only new components) merged with `ShadcnLockRepository.merge`; layer files we did not
  confidently write are omitted so a stale/edited file keeps its recorded hash.
- **Single-owner preflight**: union of the closure's manifest `api` symbols against the
  installed lock's `api` symbols (component's own symbols excluded), matching
  `LockComponentApi` semantics (map values contribute their keys).
- **Pub packages** (plan §9.1): closure package union minus `pubspec.yaml`; the delta is
  computed with `PubspecChangePlanner`, written line-preservingly, and `pub get` runs via
  the injectable `PubCommandRunner` (tests use `FakePubCommandRunner`).

## 3. API for B5 / B6

```dart
final installer = Installer(
  manifest: manifest,            // B1 RegistryManifest
  projectRoot: projectRoot,      // absolute
  reader: DirectoryRegistryFileReader(registryRoot), // or an HTTP reader
  pubRunner: const ProcessPubCommandRunner(),        // injectable
  manifestSha256: sha256OfManifest,
);
final plan = await installer.plan(['button']);       // dry-run / --json
await installer.add(['button']);                     // writes + lock + pubspec
await installer.installAll();                        // add --all
await installer.installCore();                       // init layer core
await installer.remove(['button'], force: false, purgeUserThemes: false);
```

`DryRunPlan.toJson()`/`writeHuman(logger)` and `InstallReport`/`RemoveReport` cover
`--json` and human output. B6 only needs to write `<root>/theme/app_theme.dart` and the
lock `theme` selection; `Installer` preserves the existing lock `theme` on merge.

## 6. Deviations from the brief / plan

1. **Extra B4-owned installer parts deleted** (listed in §1). Rewriting `installer.dart`
   without `part` directives made every legacy `part of 'installer.dart'` file an orphan;
   the four B4-owned ones (`installer_manifest_part`, `installer_dry_run_part`,
   `installer_config_part`, `installer_pubspec_part`) were replaced by the new files.
   `installer_pubspec_part.dart` was §5.3 "keep", but under v2 its contents are dead v1
   config/path helpers. `installer_theme_part.dart` (B6) and
   `installer_platform_alias_part.dart` (B5) were **left untouched** — they are now
   orphaned parts and must be converted to standalone libraries by B6/B5.
2. **`_topologicalLevels`/level-ordered bulk install dropped.** §5.5 says the de35dd2
   machinery survives, but decision §9.7 makes file-copy order irrelevant (the whole
   closure is copied at once). `installAll()` covers `add --all`; no dead Kahn code was
   kept.
3. **`remove` user-owned deletion is gated by `purgeUserThemes`, not `--force`.** The
   brief says "never remove user-owned files without `--force`"; the plan (§1.5, §4)
   says `--purge-user-themes`. I followed the plan: `purgeUserThemes` deletes the file,
   `force` only bypasses the "still required by dependents" refusal.
4. **`installer.dart` imports `ManifestApi` indirectly** via `manifestSymbols`; the
   direct `manifest_component.dart` import is unnecessary and was removed.
5. **Fixture ships real Dart sources.** B1's `fileHashes` are `sha256(relPath)`
   placeholders and are *not* enforced by `add` (the installer hashes the bytes it
   writes, per plan §4). The golden lock is therefore computed from the fixture bytes
   and compared byte-for-byte.
6. **`--include-preview` derives `components/<id>/preview.dart`** from the reader rather
   than the manifest (the manifest never lists previews).

## 7. Cross-batch caveats / open questions

1. **B1 validator vs. §9.7 (blocking for the real manifest).**
   `ManifestSchemaValidator._checkPrimitiveCycles` still *rejects* primitive cycles,
   but §9.7 says the real graph has cycles (`clickable ↔ clickable_state`, the popover
   cluster) and the closure must tolerate them. `manifest_closure.dart` is cycle-tolerant,
   but validating the real `registry.json` with B1's validator will fail. B1/orchestrator
   must drop or relax `_checkPrimitiveCycles`. (My fixture is acyclic, so B4 tests pass.)
2. **B5 must adapt the v1 callers of `Installer`.** `InstallerOrchestrator`,
   `presentation/cli/bootstrap.dart`, `multi_registry_*`, `commands_doctor.dart`,
   `installer_dry_run_service.dart` and the legacy tests still call `init`/`addComponent`/
   `removeComponent`/`generateAliases`/… (already broken by B1's v1 model deletion). B5
   should map commands onto `plan`/`add`/`installAll`/`installCore`/`remove`.
3. **`manifestSha256` is caller-supplied.** `Installer` does not read the manifest source
   string; B5 should compute `FileHashing.ofFile(manifestFile)` (or the remote digest).
4. **Remote registry reader.** Only `DirectoryRegistryFileReader` exists; the HTTP reader
   for plan §9.5 (GitHub raw at the release ref) is a follow-up (B5/registry-source).
5. **Registry moved / unknown units on `remove`.** Orphan detection maps a lock layer
   file back to its manifest unit; a file whose unit is no longer in the manifest is
   conservatively kept (never deleted).
6. **`update` semantics.** The brief's `add`/`update` split is served by
   `plan(overwrite: true)` + `apply`; B5's `update` still needs the B3 drift report
   (`LockDriftReport.updatablePaths`) to overwrite only unchanged, registry-owned files.
   I did not add a dedicated `update()` method to keep B4 scoped.
7. **`layers.*.units` pruning** is implemented for `remove` (foundation/theme stay as the
   always-on core; primitives are pruned). Whether `init` should ever drop the core is
   B5's `reset` concern, not covered here.
