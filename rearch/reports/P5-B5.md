# P5-B5 — Commands + registry source

Status: **done**. CLI repo `shadcn_flutter_cli` branch `refactor/rearchitecture`
(worktree clean of state-changing git ops; the orchestrator commits).

Scope: plan §8 row B5, §2, §9. Relaxed B1's cycle check, rewrote the command
surface (`init`, `add`, `remove`, `update`, `list`, `search`, `info`, `doctor`,
`dry-run`, `validate`, `audit`, `sync`, `registries`, `default`), added
`cli_parser.dart` + `command_metadata.dart` help text, and replaced the v1
registry selection with a remote-by-default, injectable, cached registry source.
Remapped or deleted every remaining v1 `Installer` caller.

## 1. B1 relaxation (plan §9.7)

`lib/src/registry/manifest/manifest_schema_validator.dart`:
- removed `_checkPrimitiveCycles` and its call — primitive cycles are legal
  (the real graph has 4: `clickable`, `overlay`, `overlay_manager`,
  `popover_overlay_state`; 90 edges). The "every referenced id exists" check in
  `_checkPrimitiveMap` is kept.
- `_declaredFiles` no longer requires a `fileHashes` entry for `themes/*.json`.
  Those files are consumed to render `app_theme.dart`, never copied; the JSON
  Schema's `hashMap` says "every copyable file", and the generated manifest
  omits all 42 preset hashes. Without this, the real manifest failed validation.

Verified against the real generated manifest
(`…/flutter_shadcn_kit/lib/registry/manifests/registry.json`): loads, validates,
sha256 `fa1d419d04c5…`, 118 components / 73 primitives / 42 themes. Closure of
`button`+`tabs` = `[button, sortable, tabs]`; `add --all` closure resolves the
cyclic primitive graph without recursion errors.

Tests updated: `test/registry/manifest/manifest_component_validator_test.dart`
(cycle now accepted; missing-dep still rejected).

## 2. Registry source (plan §9.5)

`lib/src/application/services/registry_source.dart` (rewritten):
- `RegistrySource` abstraction (`readBytes`/`readString`/`describe`/`isRemote`/
  `localRoot`) with `LocalRegistrySource` and `RemoteRegistrySource`.
- `RegistryHttpClient` seam + `HttpRegistryHttpClient` (package:http) and
  `RegistryHttpResponse`; tests inject a fake, so they never hit the network.
- `RegistryCache` (on-disk, mirrors the registry tree) — remote reads cache on
  success and fall back to it on failure; `offline: true` reads cache only.
- `RegistrySourceFileReader` adapts a source to B4's `RegistryFileReader`.

`lib/src/application/services/registry_source_resolver.dart` (new): resolves
`--registry <path|url>` → `SHADCN_REGISTRY_ROOT`/`SHADCN_REGISTRY_URL` →
`.shadcn/config.json` (`registryPath`/`registryUrl`) → default remote
`https://raw.githubusercontent.com/mibrar-dev/shadcn_flutter_kit/<ref>/
flutter_shadcn_kit/lib/registry`, where `<ref>` = `v<CLI version>`. Remote
sources always get a cache at `<project>/.shadcn/cache/registry`.

`lib/src/application/services/registry_manifest_loader.dart` (new): reads
`manifests/registry.json`, decodes, runs `ManifestSchemaValidator`, returns the
model + sha256 + raw JSON; throws `RegistryManifestException` (missing / bad
JSON / schema-invalid).

`lib/src/presentation/cli/command_context.dart` (new): one resolver builds the
`ShadcnConfig`, source, loaded manifest, B4 `Installer` and B6 `ThemeService`
sharing one install root; every registry-backed command uses it.

## 3. Commands

- `init` — `--dir` (default `lib/ui/shadcn`), `--theme` (default `vercel`),
  `--yes`, `--json`. Installs the foundation+theme core via B4, picks a preset
  (explicit → `--yes`/`--json`/non-TTY default → TTY prompt), writes
  `.shadcn/config.json`, then calls B6's `ThemeService.apply` (no re-implemented
  theme logic).
- `add <ids…>` — `--dry-run`, `--json`, `--force`, `--all`, `--include-preview`;
  closure + single-owner preflight + verbatim copy + lock v2 via B4.
- `remove [ids…]` — `--all`, `--force`, `--purge-user-themes`, `--json`.
- `update [ids…]` — **new**; `--all`, `--check`, `--json`. New
  `application/services/update/update_service.dart`: hash-driven (overwrite
  unchanged, report locally modified, report removed-upstream, restore missing),
  never touches user-owned files, regenerates `app_theme.dart` through an
  injected B6 callback. `--check` reports only; exits `1` when behind/modified.
- `list` / `search` / `info` — read the manifest directly (no index.json);
  `info` prints the closure, files, api, theme class and the computed import
  path (`<installRoot>/<entry>`, not the wrong meta string).
- `doctor` — manifest+closure+layout+lock drift+user-owned+pubspec+import-guard;
  exits `0/1/2/3` per plan §2.5.
- `validate` — validates the manifest against v2 (exit `20` on violation).
- `audit` — installed-vs-lock drift (exit `50` on drift).
- `dry-run` — thin alias of `add --dry-run`.
- `sync` — re-materialises the installed closure and refreshes the locked theme.
- `registries` / `default` — rewritten without `MultiRegistryManager`, reading
  `.shadcn/config.json` + the optional registry directory.
- `cli_parser.dart` / `command_metadata.dart` / `usage.dart` — `update` added;
  `assets`/`locale`/`platform`/`deps` retired; `--registry <path|url>` replaces
  the three hidden v1 selector flags; `--json` hoisting covers the new set.
- `bootstrap.dart` / `bootstrap_dispatcher_builder.dart` — v2 entry + dispatcher;
  `docs`/`theme` help routing preserved.

## 6. Deviations / notes

- Also relaxed `fileHashes` coverage for `themes/*.json` (not just the cycle
  check). Required for `doctor`/`validate` to accept the generated manifest and
  for B6's `ThemeRegistrySource` (which now runs the full validator).
- `docs/reference/commands/**` regenerated and `doc/user/commands.md`-driven
  command-matrix assertions replaced with metadata-vs-parser assertions, since
  the retired commands changed the documented set.
- Cross-batch one-line fixture fix: `test/fixtures/theme_registry_v2/components/
  button/button.dart` imported `../../../theme/theme.dart` (outside the fixture
  root) and left it unused; corrected to `../../theme/theme.dart` and used, so
  `dart analyze` is clean. B6 owns that fixture.
- `bootstrap.dart` keeps `docs`/`theme` help short-circuits; registry resolution
  is lazy per command, so `--help` never touches the network.
- `init` writes `.shadcn/config.json` with `installPath`/`themeId` and the
  resolved `registryPath`/`registryUrl`; B6's theme service records the lock
  `theme` entry.
- `project refresh` and `sync` re-run the installed closure + locked theme
  (the v1 inline-init refresh machinery was deleted with `multi_registry`).
- `feedback` now passes a static registry context (the v1 resolver needed the
  deleted multi-registry machinery); feedback still works.

## 7. Open questions

- `theme` (B6) resolves its registry from `.shadcn/config.json` only, so
  `theme list/apply` before `init` does not honour `--registry`; the theme
  command is B6's file and was not edited.
- `init` relies on the manifest `packages` of the foundation/theme units for
  pub deps; the real core declares none, so `intl`/`flutter_localizations`
  arrive only when a component that needs them is added (plan §2.1/§9.1).
- `registry.manifestSha256` is refreshed by `update`; `doctor`/`audit` flag
  “registry moved” but do not auto-refresh.
- `update` does not yet install brand-new upstream files for an already
  installed component (plan §2.3 only specifies unchanged/modified/removed).

## 8. Exit-code mapping (verified against the real CLI)

- missing/unreadable manifest or bad local `--registry` path → `10`
  (`registryNotFound`); `RegistryManifestException.notFound` distinguishes this
  from a schema violation.
- malformed JSON / schema-invalid manifest → `20` (`schemaInvalid`).
- offline with no cache → `41` (`offlineUnavailable`); other transport failure
  → `40` (`networkError`).
- unknown component → `30`; single-owner/closure/lock/theme failure → `50`.
- `doctor` → `0/1/2/3`; `update --check` → `1` when behind/modified.
