## 3. `theme apply` contract

`apply <preset>` resolves the preset from the manifest `themes` map (by id, then
by display name, both case insensitive), reads `themes/<id>.json`, validates it
against `themes.schema.json`, renders `app_theme.dart` and records the
selection in `shadcn.lock`. Then:

| on-disk state | without `--refresh` | with `--refresh` |
|---|---|---|
| file missing | write, `created` | write, `created` |
| matches the lock | nothing written, `unchanged` | nothing written, `unchanged` |
| differs, but equals the lock digest (CLI-owned, i.e. a preset switch) | write, `refreshed` | write, `refreshed` |
| differs from the lock digest (`modified`) | **refused**, `drift`, exit 50 | write, `refreshed` |
| exists with no lock entry (`untracked`) | **refused**, `drift`, exit 50 | write, `refreshed` |

Two decisions worth the QA reviewer's attention:

1. **The lock digest is compared against the file, not against the preset id.**
   The first implementation only trusted the lock digest when the locked preset
   *was* the requested one, which made a plain `vercel -> claude` switch look
   like drift. Fixed: `recordedSha256` is taken from the lock whenever the lock
   records a `theme.path` equal to the target, whoever wrote it.
2. **A refusal does not touch the lock or the config.** Recording the new
   preset id while the old bytes stay on disk would make `doctor` report a clean
   tree over a file nobody asked for. `_persistConfigThemeId` takes
   `onlyIfApplied` for the same reason.

## 4. API for B4 / B5

```dart
// One call for init / add / update (extension on Installer, batch B6):
Future<ThemeApplyResult?> installer.applyThemePreset(
  String presetId, {
  bool refresh = false,
  ThemeRegistrySource? source,   // reuse a reader you already have
  String? namespace, String? registryPath, String? registryUrl, bool offline = false,
});

Future<List<ThemeCatalogEntry>> installer.listThemePresets({...same options});
Future<ThemeCatalogEntry?>     installer.promptThemePreset({...same options});
Future<ThemeService>           installer.themeService({...same options});

// Without an Installer (the `theme` command does this):
final service = await ThemeService.resolve(
  projectRoot: ..., installRoot: ..., namespace: ..., registryPathOverride: ...,
);
await service.apply('vercel', refresh: false);
final presets = await service.listPresets();
```

`applyThemePreset` returns `null` (after a warning) only when **no registry is
configured at all**, so `init` can install the core and let `theme apply` finish
later. A configured-but-unreadable registry throws, because silently skipping
would hide a real misconfiguration.

`ThemeRegistrySource.overReader(read, registryRoot:, describe:)` adapts any
reader with that shape. B5's `RegistrySource` plugs in directly:

```dart
ThemeRegistrySource.overReader(
  source.readString, registryRoot: source.localRoot, describe: source.describe,
);
```

Verified against `LocalRegistrySource` at runtime (printed the fixture's
`[claude, vercel]`).

## 7. Findings

1. **`B1`'s `ManifestSchemaValidator` rejects the real kit manifest**, for two
   reasons, both verified against `flutter_shadcn_kit/lib/registry/manifests/registry.json`:
   - *primitive dependency cycles* — 10 real two-way cycles (`clickable <-> clickable_state`,
     `overlay_manager <-> overlay_manager_layer`, the popover cluster). Plan §9.7
     already says cycles are legal; the validator still rejects them.
   - *`fileHashes` coverage* — `themes/<id>.json` are declared files but carry
     no digest (651 hashes, none under `themes/`).

   Because of this, `ThemeRegistrySource.loadManifest()` deliberately validates
   **only what the theme flow needs** (`schemaVersion == 2`, plus a well-formed
   `themes` map) instead of calling the full validator. `validate` / `doctor`
   should own whole-manifest validation and will need both fixes. A tripwire test
   (`theme_preset_validator_test.dart`) pins the two known gaps so they surface
   loudly when B1 lands the fix.
2. **The generated file is not `dart format` clean with relative imports.**
   The tall style wants a blank line between the `package:` and the relative
   import group. The kit's generator emits none, and its own format test passes
   because it always runs with the `package:` form. The CLI's real output uses
   the sibling-relative form (`theme.dart` next to `color_tokens.dart`), so a
   user's `dart format` would add that one blank line. Fixing it properly means
   a one-line change in the kit generator **and** the same change in this port;
   I kept byte-identity as the brief requires and pinned the exact difference in
   a test. **Decision needed** (see below).
3. **`app_theme.dart` is user-owned in the lock's eyes only via `theme`.** B3's
   `ShadcnLock.ownerOf` returns the layer key `theme` for both `theme/theme.dart`
   and `theme/app_theme.dart`; consumers must disambiguate by path. `apply` only
   ever writes the latter.

## 8. Deviations

1. **`installer_theme_part.dart` is no longer a `part`.** B4's rewrite of
   `installer.dart` removed every `part` directive, so the file had to become a
   standalone library. It keeps the `InstallerThemePart` extension name, so
   `installer.applyThemePreset(...)` reads the same to callers.
2. **`lib/src/installer.dart` gained one export line** so the extension stays
   reachable through the single installer import. Nothing else in the CLI is
   coupled to the theme code: `theme_command.dart` builds a `ThemeService`
   itself and only takes `projectRoot`/`installRoot` from the `Installer`.
3. **The widget-theme surface is deleted, not stubbed** (plan §9.3, clean
   break). `theme widget`, `--apply-file` and `--apply-url` exit 2 with a
   message pointing at `theme list` / `theme apply`; `theme import` is still
   future work (plan §7.7).
4. **Drift exits `50` (`validationFailed`)**, the closest existing code. There
   is no dedicated "refused" code and the exit-code table is meant to stay
   unchanged (§6.4).
5. **Preset ids are matched by display name too** (`theme apply Claude` works),
   preserving the old `_findThemeIndexEntry` behaviour rather than tightening it.
6. **`theme import` is not implemented** — out of scope per plan §7.7.
7. **`theme_css.dart` is untouched** (plan §5.2 keeps it for `theme import`); it
   still imports the v1 loaders, which is fine while it is unreferenced.

## 9. Open questions for the orchestrator

1. **Should the kit generator emit the import-group blank line?** If yes, it is
   a one-line change in `tool/rearch/gen_app_theme.dart` plus the same line in
   `app_theme_generator.dart`, and the golden test keeps proving they agree. If
   no, the relative-import form stays non-canonical and every user's formatter
   will touch the generated file once.
2. **Does the `app_theme.dart` header comment stay kit-flavoured?** It says
   `// Regenerate: dart run tool/rearch/gen_app_theme.dart <id>.json
   app_theme.dart`, which is wrong advice in a user's project (they should run
   `flutter_shadcn theme apply <id>`). Byte-identity with the kit forced me to
   keep it; changing it in the CLI alone would break the golden test.
3. **Drift exit code.** 50 is a compromise; if the orchestrator wants a
   dedicated code (or wants drift to exit 0 as a warning), say so and it is a
   one-line change in `theme_command.dart`.
4. **Should `theme list` accept a query** (`theme list dark`)? Not in plan §2.4;
   `search` exists for components only.
