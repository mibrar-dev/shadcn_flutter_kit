## 2. Component categories

The taxonomy from the brief was adopted verbatim (no renames) with one
clarification recorded here: the last value is written
`Utilities (building blocks)` and holds exactly the 21 components that P6-F3
marked `"listed": false`, so "building block" in the docs and
"unlisted" stay the same set.

Mapping reasons (only the ones that are not self-evident):

* `button`, `toggle` → **Buttons & Actions** — pressable actions, not forms.
* `command`, `context_menu`, `dropdown_menu`, `menu`, `menubar`,
  `triple_dots` → **Menus** — the popup-item families; `context_menu` was
  `overlay` before but is a menu by behaviour.
* `alert`, `progress`, `skeleton`, `spinner`, `toast` → **Feedback** —
  shadcn groups these; `toast` stays here even though it renders in an
  overlay, because its role is feedback.
* `code_snippet`, `image`, `markdown` → **Typography & Media** — the three
  text/asset surfaces that are not interactive.
* `color_field`, `color_input`, `color_picker`, `eye_dropper` → **Color** —
  they are colour tools first and form fields second (they are still
  installable and interactive).
* `calendar`, `date_picker`, `time_picker` → **Date & Time**.
* `border_loading`, `dot_indicator`, `text_animate` → **Animation & Effects**.
* All 21 `listed: false` components → **Utilities (building blocks)**.

## 3. Blocks layer

`lib/registry/blocks/<id>/` is layer 4, above components. Files per block:

* `<underscored_id>.dart` — the public widget **and** the preview (there is
  no `preview.dart`), so the docs page renders exactly what an app renders;
* optional `<id>_<part>.dart` parts (used by `dashboard-01` and
  `dashboard-02`);
* `meta.json` — `id`, `name`, `category`, `description`, `viewport`,
  `install`, `import`, `tags`, `deps{foundation,theme,primitives,components}`,
  `files[]` (Dart + README);
* `README.md` — files, install command, deps table, customization notes.

The block's Dart file stem replaces `-` with `_`: `dashboard-01` lives in
`dashboard_01.dart`. This is forced — `package:flutter_lints` enables the
`file_names` lint, and a hyphenated file name is a lint error, which the
"zero analyzer issues" gate rejects. The mapping is mechanical and is stated
in `tool/registry/README.md`.

A block imports only foundation/theme/primitives/components. The
`block-imports` rule in `check_layers` fails the build if a block imports
another block; `check_layers` also treats `blocks/**` as layer 4, so a
component importing a block is now a `layer-direction` error.

## 4. Manifest, schema and generator

`tool/registry/src/registry_manifest.dart` now reads `blocks/*/meta.json` and
emits a `blocks` map keyed by id, with `name`, `category`, `description`,
`viewport`, `entry`, `files`, `docs`, `deps`, `tags`, `install`, `import`
(and `packages` when the block imports a non-flutter package). Each block's
README is added to `fileHashes` (so a docs edit is detectable) but is **not**
listed in `files` (never copied into an app). `install.blocksDir` is `blocks`.

Validation added to the generator (all `ManifestBuildException`, so
`--check` fails rather than emitting a bad manifest):

* component `category` is in `componentCategories`;
* block `category` is in `blockCategories`, `viewport` in
  `{desktop, mobile}`;
* block `deps` has exactly the four layer keys, every layer id exists, and
  `deps.components` holds only component ids;
* every block has `README.md` and the entry file, and every file listed in
  `files` exists.

`_blockJson` computes `packages` over the Dart files only. A first version
ran it over every entry of `meta.files`, which includes `README.md`, and
`directiveUris` then parsed the README's fenced Dart snippet and found
`import 'package:<your_app>/…'` — the walk-up for the `flutter_shadcn_kit`
package root failed because the generator rejects an unknown package.

### Schema diff (`rearch/reports/registry_manifest.v2.schema.json`)

* `required`: added `"blocks"`.
* `properties`: added `blocks → #/$defs/blockMap`.
* `$defs` added: `blockCategory` (enum of the six block families),
  `blockCategoryList`, `block` (required `name, category, description,
  viewport, entry, files, docs, deps, tags, install, import`), `blockDeps`,
  `blockMap`.
* `$defs.component.category`: `{type: string, minLength: 1}` →
  `$ref: #/$defs/componentCategory` (enum of the 13 component categories).
* `$defs.relPath.pattern`: `\.(dart|json)$` → `\.(dart|json|md)$` (block
  READMEs).
* `$defs.installInfo`: `required` and `properties` gained `"blocksDir"` with
  `const: "blocks"`.
* `description` of the schema now mentions the blocks layer and P6-B1.

## 5. `check_layers` changes

* `_layerOfRelPath` maps `blocks` to layer 4 (was unmapped → no rule fired).
* New rule `block-imports` (error): a block importing another block.
* New rule `block-installable` (error): per-block
  `meta.json` + id match + `README.md` + category + viewport + entry file +
  every listed file exists + every Dart file under 400 lines.
* `_checkLayerDeps` is now shared by components and blocks via the `_Buildable`
  interface, so its message names either "component" or "block".
* `layerRuleIds` and the CLI usage list carry the two new ids.

## 8. Findings

* **`tabs` overflows 41px at 375px** when three labels do not fit. This is a
  *component* bug, not a block one; the blocks that use `Tabs` wrap it in a
  horizontal `SingleChildScrollView` (the same workaround the `tabs` preview
  uses). Reported under "missing component features" below.
* **`ShadcnImage` asserts `width != null || height != null`**, so the
  `aspectRatio`-only form the doc comment advertises is unusable. `login-02`
  passes `height: 180` (stacked layout) and
  `height: constraints.maxHeight` (split layout) instead.
* **`Badge` has no `success`/`warning` variant** (only primary/secondary/
  outline/destructive), so `dashboard-01` draws its status pills from the
  chart tokens + `withValues(alpha:)`.
* **`Progress` is the only progress primitive**: `LinearProgressIndicator` is
  Material-only and banned, so `sidebar-03`'s storage meter uses `Progress`.
* The four chart-like visuals in the dashboards are `Container`s and a
  `CustomPainter` fed by the `chart1..chart5` tokens, because the registry
  has no chart component.
* No Material or Cupertino import anywhere in the new files (the `banned:`
  gate line is empty).

## 9. Open questions / missing component features

1. `tabs` overflows on a narrow stage (see §8). A fix inside `tabs` would
   remove the `SingleChildScrollView` wrapper every block and preview needs.
2. `ShadcnImage` doc comment vs. the `width`/`height` assertion should be
   reconciled (either accept `aspectRatio` alone, or fix the doc).
3. `Badge` would benefit from semantic variants (`success`, `warning`,
   `info`) — the blocks currently re-implement pills for them.
4. `Input` has no label slot, so every form field in a block pairs two
   widgets (`Text` label + `Input`). A `label`/`field` component would halve
   the block code.
5. Blocks are all `viewport: desktop`. A `mobile` block family (a phone
   shell, a bottom-sheet dialog set) would exercise the other hint value.
6. `docs/**` is out of scope for this unit, but the Blocks page, the block
   sidebar and the ⌘K palette still need the P6-B1 `blocks` map wired in.
