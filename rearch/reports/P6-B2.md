## 2. Resolution model

`add <id>` now has **one address space**: `ManifestClosureResolver.resolve`
takes the typed ids and seeds each one as a component when the manifest has
one, as a block when it has that, and throws
`ManifestClosureException('component or block', id)` when it has neither. The
explicit `blockIds:` argument remains for callers that *know* the ids are
blocks and nothing else (`add --all --blocks`, `sync`, `project refresh`).

* an id that names neither never silently installs nothing;
* a registry without a `blocks` map still reports `Unknown component id ...`
  (the message only widens once the registry publishes blocks);
* the error maps to exit `30` (`componentMissing`) exactly as before.

A block may not depend on another block (P6-B1 `block-imports`), so a block is
never pulled in transitively: `closure.blocks` is exactly what was asked for.

## 3. Manifest, schema and file layout

* `lib/src/registry/manifest/manifest_block.dart` (new) — `ManifestBlock`
  (id, name, category, description, viewport, entry, files, docs, deps, tags,
  install, import, packages) and `manifestBlockViewports`
  (`desktop`, `mobile`). `deps` reuses `ManifestComponentDeps`: a block has the
  same four layer keys, so there is no second shape. A block has no `api` and
  no `userOwned`.
* `RegistryManifest.blocks` + `ManifestInstall.blocksDir` (default `blocks`,
  fixed by the schema). `declaredFiles` now covers block files; block `docs`
  are deliberately excluded (never copied).
* `$defs` rules ported to the validator
  (`manifest_block_checks.dart` (new) + `manifest_theme_checks.dart` (new),
  split out of `manifest_component_checks.dart` so every file in that
  directory stays under 400 lines):
  * `blocks.<id>` keys are exactly name/category/description/viewport/entry/
    files/docs/deps/tags/install/import/packages — **no `api`, no
    `userOwned`, no `theme`**;
  * `viewport` ∈ {desktop, mobile}; `entry` is `blocks/<id>/<file>.dart`;
  * `files` are Dart only and under `blocks/<id>/`; `docs` are markdown only;
  * `deps.components` may name components only — a block id is rejected;
  * a block id may not also be a component id (one address space);
  * `fileHashes` must cover every block file, and markdown keys are now legal
    (the kit stores each block README digest there).
* `blocks` is **optional**: a manifest written before P6-B1 has none and stays
  valid, which is also why the v2 fixture used by 20 existing tests still
  passes untouched.
* `relPathPattern` widened from `\.(dart|json)$` to `\.(dart|json|md)$`, to
  match `$defs.relPath` in
  `rearch/reports/registry_manifest.v2.schema.json` (P6-B1) — without it the
  CLI rejects the real kit manifest.

## 4. Install, lock, update, remove

* `InstallerFileInstaller`: `blocksDir` joins `componentsDir`/`layerDirs` in
  `targetPathFor` and in the import guard, so
  `blocks/login-01/login_01.dart` → `<root>/blocks/login-01/login_01.dart` and
  a block's relative imports are checked like any other file. A block→block
  import stays *inside* `blocks/` and is therefore not an import-guard error
  (layer direction is the kit's `check_layers` `block-imports` rule); a test
  documents that boundary explicitly.
* `installer_plan_part.dart` (new) — the file-planner extracted from
  `Installer` (decision-only: reads bytes, compares digests, writes nothing).
  `Installer` is back under 400 lines (324).
* `installer_lock_part.dart` records a block with `ShadcnLockBlock` (id,
  version, files→sha256, deps). A block owns **no** user-owned path, so
  `updatablePaths` always contains its files and `update` may refresh any
  block file whose bytes still match the lock — the same rule as a component.
  `DryRunPlan` carries `blocks` + `requestedBlocks`.
* `ShadcnLock` (`shadcn_lock_block.dart` (new)): `blocks[]`,
  `blockIds`, `blockFor`, `upsertBlock`, `removeBlock`, block files in
  `registryOwnedPaths` / `ownerOf` / `dependentsOf`, block files in
  `ShadcnLockRepository.inspect` (so `audit` and `doctor` see them), and
  `"blocks": []` always written next to `"components": []`. An absent `blocks`
  key still parses (pre-layer locks).
* `remove`: a block deletes exactly its own files and nothing else — the
  components it assembled stay installed. A component a block still needs is
  refused (`Cannot remove input; required by login-01`) unless `--force`.
  Orphaned layer pruning now counts the remaining blocks' deps.
  `remove --all` clears components and blocks together with no refusal.
* `update`: pass 1 covers tracked block files, pass 2 installs files the
  manifest added to an installed block, `_recordNewFile` routes
  `blocks/<id>/…` to the block record, and `UpdateLockBuilder` upserts it.
  `update login-01` (block id) and `update button` (component id) each stay in
  their own lane.
* `sync` and `project refresh` re-apply installed blocks too; `doctor`'s
  import-depth guard now includes block files.

## 5. Commands and output

`lib/src/presentation/cli/catalog_entry.dart` (new) is the one place that
knows a `list`/`search` row may be a component or a block: `CatalogEntry`
(id, name, **category**, description, tags, kind, viewport), `matches`,
`filterByCategory`, `groupByCategory` (categories alphabetical, entries by id)
and `writeGroupedCatalog`.

| command | behaviour |
|---|---|
| `list` | components grouped by category; JSON `{kind, count, categories, components, blocks}` |
| `list --blocks` | blocks grouped by category, with the `[viewport]` tag |
| `list --category <c>` | case-insensitive filter on the shown list, with a "try `list --blocks`" hint when the miss is a taxonomy mismatch |
| `search <q>` | matches components **and** blocks; each row shows `[category · kind]`; `--category` filters |
| `info <id>` | component (api, user-owned files) or block (viewport, install, docs, closure); JSON `kind` |
| `add <id>` / `dry-run <id>` | polymorphic ids |
| `add --all --blocks` / `dry-run --all --blocks` | opt-in bulk blocks (never implicit in `--all`) |
| `remove <id>` / `remove --all` | component + block ids; `removedBlocks` in the report |
| `update <id>` | component or block ids |

JSON stays stable: existing keys keep their names and order, the additions
(`blocks`, `requestedBlocks`, `removedBlocks`, `kind`, `viewport`, `category`)
are additive, and every list is deterministically sorted.

Help text (`--help` on `add`, `dry-run`, `remove`, `list`, `search`, `info`),
`command_metadata_components.dart` and the regenerated
`doc/reference/commands/**` all describe the blocks layer; `README.md` gained a
**Blocks** section and the `blocks/<id>/` layout line.

## 8. Findings / decisions worth reviewing

1. **`blocks` is optional in the CLI validator, required in the kit schema.**
   The kit's `registry.json` now always emits `blocks`; the CLI accepts a
   registry that has none, so third-party and pre-P6-B1 manifests keep
   loading. `list --blocks` on such a registry prints "No blocks in this
   registry."
2. **`add --all` does not install blocks.** 16 finished screens would land in
   an app that only asked for "every component"; `--all --blocks` is the
   explicit opt-in.
3. **A block owns no user-editable file.** Its `README.md` is documentation
   and is never copied, so `update` may always refresh a block file whose
   bytes still match the lock. If the design later wants a user-owned
   `blocks/<id>/…` seam, it needs a new lock field.
4. **Component and block taxonomies are independent** (13 categories vs 6
   families), so `list --category Authentication` on the component list is
   empty by design; the CLI prints a hint instead of a bare "no match".
5. `docs/**` in the kit repo is still untouched (P6-B1 open question 6): the
   Blocks page, block sidebar and ⌘K palette are not wired to the new
   manifest `blocks` map by this unit.
6. `install.blocksDir` is `const: "blocks"` in the schema, so the CLI hardcodes
   the string and rejects anything else rather than guessing a layout.
