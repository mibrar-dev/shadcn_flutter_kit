## 2. Data model (generic, not mockup-shaped)

- **docs_data**: `DocsComponent{id,name,category,description,install,import,fileCount,stability}`,
  `DocsPreset{id,name,modes}`, `DocsCategory{id,count}`, `DocsStats{components,presets,materialImports,modes}`.
  `fileCount = manifest files + userOwned` (CLI-installed Dart files; previews
  and user-owned files are excluded from the manifest `files` list, verified).
  `stability` is `'stable'` for every component with the derivation documented
  in the class doc — the manifest has no stability field yet.
- **docs_api**: `DocsApiTable{componentId,symbol,hasApiTable,parseClean,summary,params}` +
  `DocsApiParam{name,type,isRequired,defaultValue,doc}`; `DocsThemeTable{componentId,themeClass,themeDefaults,userFile,userOwned,hasTheme,fields}` +
  `DocsThemeField{name,type,description}`. Maps are complete for all 118 ids.
- **docs_tables**: `DocsKeyboardRow{keys,action,source}` per component (empty =
  gap), `kKeyboardGaps`, `DocsDep{id,kind}` per component (component edges
  flagged via `DocsDepKind`), `kRelatedIds` (≤3 same-category neighbours,
  deterministic wrap-around), and the parsed CLI snapshot as
  `DocsCliCommand{label,invocation,usage,summary,helpText,flags}` +
  `DocsCliFlag{name,alias,placeholder,description}`.
- **docs_search**: `DocsSearchEntry{label,kind,route,tag,keywords}`; 118
  component entries (keywords = name + manifest tags), 12 command entries,
  42 preset entries (keywords = display name).
- **docs_snippets**: `DocsSnippet{id,componentId,language,code,tokenClasses}` +
  `spans(...)` builder; `kComponentFileLists` (install-root-relative files +
  user-owned files) and `kUserOwnedNote`.
- **app_theme**: 42 `build<Id>Theme(Brightness)` factories + `kDocsDefaultPresetId`
  + `buildDocsTheme(String, Brightness)` dispatcher with a documented fallback.
- **component_previews**: `loadComponentPreview(String) -> Future<Widget>`.

The model covers the shadcn-site spec's needs (catalog, install command +
manual file list, README examples, API reference table, theme fields,
keyboard/a11y, deps, related, presets, CLI reference, search) without any
mockup-specific section.

## 3. Key decisions and findings

### 3.1 `app_theme.dart` is the kit generator's output by construction

`render_code.dart` imports the kit tool source
(`flutter_shadcn_kit/tool/rearch/gen_app_theme.dart`, a VM-only library) and
calls `ThemeValues.toDartSource()` per preset; the docs file is the shared
header/imports + all 42 verbatim bodies + the dispatcher. The test asserts,
per preset, that the checked-in file contains the kit generator's body
byte-for-byte: **42/42 byte-equal**. `kDocsDefaultPresetId` is asserted equal
to `kDefaultDocsPresetId` (`state/docs_state.dart`); a stale localStorage id
falls back to modern-minimal instead of throwing.

### 3.2 Code highlighting is codegen-owned, 4 classes, compact

Dart blocks are classified with the `package:analyzer` tokenizer (comment /
keyword / string / plain; whitespace = plain); bash gets a documented
character scanner (comments, quotes, command-position words + flags); JSON a
minimal scanner (strings, `true/false/null`, comments). Output is one class
character per code character (`p/c/k/s`), and the generated `spans()` builder
merges runs — 290 snippets (282 dart, 8 bash) for ~190K of source instead of
per-token `TextSpan` constructors. The test round-trips every button/dialog/
command snippet against the README and asserts the class map's length/alphabet.

### 3.3 API extraction: entry-file constructors only, per plan §2.2

Primary class preference: `<DisplayName>`, `<id>`, then manifest `api.classes`
that are `StatelessWidget`/`StatefulWidget` in the entry file. 110/118
components get a parameter table (required-first; types/doc from the matching
field declaration); the 8 function-first/no-widget entries
(`autocomplete, formatter, dialog, drawer, popup, alpha, color, locale_utils`)
emit an empty table with `hasApiTable: false` — the plan's explicit "never
invent" rule. `parseClean: false` marks the three entry files analyzer 6.4.1
cannot fully parse under Dart 3.13 (`badge`, `scaffold`, `swiper`; D1 §6
heads-up, 9 registry files total, 6 of them primitives).

### 3.4 Keyboard tables: conservative, gaps explicit

Rows come only from README sections whose heading matches
`keyboard|a11y|accessib|behavio(u)r`, and only from Markdown key tables
(`| Key | Effect |`) or backticked/bold key tokens; every key token must match
a known key name or modifier combo. Result: rows for 3 components
(`autocomplete`, `calendar`, `radio_group`), 115 gaps. `kKeyboardGaps` lists
every gap (also printed by every tool run) and the file header says to extend
the component README — never this file. `dialog`, which documents Esc/trap/
restore in prose outside a matching heading, is an explicit gap.

### 3.5 CLI snapshot (input) is hand-maintained and parsed, not invented at runtime

`tool/cli_snapshot.txt` is the P5 §2 command surface rendered as
`--help`-style text (sections start `$ flutter_shadcn … --help`; flag lines
`--flag=<value>  description`). The parser is documented in the file header
and in `readme_scan.dart`. **UNVERIFIED against a real CLI** — the new CLI does
not exist yet; when it ships, re-paste the real help text and the page/parser
stay as-is (missing sections fall back to snapshot-only rendering, per plan
§3-08). 12 commands × flags are generated into `kCliCommands` and the search
index.

### 3.6 Previews: how they reach the docs app (brief asked to report this)

**Verified today:** the mirror DOES include all 118 `preview.dart` files —
`docs/tool/sync_registry.sh` lines 16-20 say so explicitly, P6-D1 report §3.10
records the decision, and the manifest `fileHashes` cover them (651 hashes =
533 Dart + 118 previews). The D2 brief's assumption "mirror excludes
preview.dart today" is stale; the brief's own first sentence ("except where
the plan says previews are loaded") matches the plan §2.1/D4.

Therefore `lib/previews/component_previews.dart` generates 118 deferred
imports of `package:docs/ui/shadcn/components/<id>/preview.dart` (prefixes
`preview_<id>` — the alias must not collide with keywords, e.g. `switch`) and
a `loadComponentPreview` switch that awaits `loadLibrary()` then constructs
`<Class>()` (deferred classes cannot be `const`; verified with the analyzer).

Relocating previews to a docs-owned `lib/previews/sources/` (brief
parenthetical) requires changing `sync_registry.sh` **and** the planned
`mirror-check` job (P6 plan §2.3 requires every manifest relPath at
`docs/lib/ui/shadcn/<path>`, previews included), i.e. D1-owned files that are
not in D2's output list. Recommendation to the orchestrator: keep D1's design
(previews under the mirror, hash-covered) or schedule the relocation as an
explicit D1/D4 follow-up; D2 followed the verified tree.

### 3.7 `--check` + formatting

Every generate/check run formats outputs with `dart format --output=write`
(the tool spawns the SDK formatter), so generated files are always
format-clean. `--check` regenerates into a temp dir inside `.dart_tool/` —
required because `dart format` applies the package language version only to
files inside the package (a `systemTemp` copy formats differently and would
produce false drift). Self-tested: fresh passes, one mutated byte fails with
`out of date`.

### 3.8 Tool size

The brief estimated ~700 LOC; the tool + tests are 3,729 LOC (445 of them the
test) because seven renderers + three parsers were needed. Per the repo's
~400-line rule the tool is split into `tool/src/` modules (largest 418 lines)
with the entry keeping only CLI/write/check logic. `gen_docs_data.dart` exports
all modules so the test uses one import.

## 5. Open questions / flags

1. **Function-first APIs** (8 ids incl. `dialog`): the plan says empty table +
   snippets only, and D2 follows it. The shadcn-site spec's component pages
   show an API reference; if `dialog` needs `showShadcnDialog` params, a later
   batch must extend the model deliberately (READMEs already document them).
2. **Analyzer 6.4.1** cannot parse 9 registry files under Dart 3.13
   (3 entry files flagged `parseClean: false`); facts for those are
   best-effort. A future kit batch could bump the dev dependency.
3. **`dart format` language version**: generated-file freshness depends on
   the checkout's language version; the tool documents and handles this
   (temp dirs inside `.dart_tool`). CI should run `--check` from `docs/`.
4. **Generated size**: ~884K source total (`docs_api.dart` 345K, snippets
   190K). D4/D6 should measure the JS budget; if it matters, the API/snippet
   maps can be split by tree-shaken imports later (deterministic tool change).
5. **CLI snapshot is synthetic** until the CLI exists (see §3.5); keep it
   hand-maintained, never parse docs pages for flags.
6. **Keyboard gaps (115)**: closing them is a registry README task; the tool
   picks up new sections automatically and the gap list shrinks.
7. `stability` (docs_data) is the one non-manifest presentation constant;
   derived and documented, drop it when the manifest grows a field.
