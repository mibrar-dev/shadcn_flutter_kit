## The mechanism

`lib/registry/theme/density.dart` gained two **const** constructors on the existing
`EdgeInsetsDensity` (no new mechanism, no new file):

```dart
class EdgeInsetsDensity extends EdgeInsets implements DensityEdgeInsetsGeometry {
  const EdgeInsetsDensity.pxSymmetric({double horizontal = 0, double vertical = 0});
  const EdgeInsetsDensity.pxAll(double px);
}
```

Each side is stored as the shadcn px value divided by `Density.pxBase` (16, the
default `baseContentPadding`), so `EdgeInsetsDensity.pxSymmetric(horizontal: 8,
vertical: 2)` is exactly shadcn `px-2 py-0.5`. `Density` also gained:

```dart
double get scale => baseContentPadding / Density.defaultDensity.baseContentPadding;
static const double pxBase = 16.0;
```

which is the `scale = baseContentPadding / 16` factor `button.dart`'s
`_buttonMetricsFor` already spelled out per size. So the const default carries the
shadcn value, and the single build-time call

```dart
resolveEdgeInsets(value, ambient.density.baseContentPadding * ambient.scaling)
```

(the same call `dialog.dart:317` and `input_style.dart:339` already made) turns it
into px. `resolveEdgeInsets` is a no-op for a plain `EdgeInsets`, so a user's
literal override still passes through untouched. Gaps read `theme.spacing.<step>`
(`xs`=4, `sm`=8, `md`=12, `lg`=16, `xl`=24, `xxl`=32 at the default base 4).

## The 3 icon-geometry bugs

| bug | before | after |
|---|---|---|
| `chip.dart` row order | `[content, Gap, leading, Gap, trailing]` — the leading icon rendered **after** the label, measured 84px from the outer edge | `Row` built first, `Padding(density-resolved)` wraps the whole row → leading icon 8px from the edge (shadcn `px-2`), `Gap(theme.spacing.sm)` (= 8, shadcn `gap-2`) from the label. `Directionality` mirrors the slots, so RTL works. |
| `badge.dart:157` | `Padding` wrapped only `child`, so the leading icon started at x = 0 — exactly the "icon touching the edge" the requirement forbids | Same row-then-pad structure as chip: 8px edge, 8px gap. |
| `chip.dart`/`badge.dart` padding | raw `EdgeInsets.symmetric(horizontal: 8, vertical: 2)` | `EdgeInsetsDensity.pxSymmetric(horizontal: 8, vertical: 2)` resolved at build. |

### Test assertions that were wrong vs shadcn — changed and why

1. **`layout_audit_shadcn_values_test.dart:149` "header cell padding matches its
   documented value"** did `expect(tableHeadCellPadding,
   const EdgeInsets.symmetric(horizontal: 8))` — a comparison against a literal that
   no longer exists. It now resolves the constant at the default density
   (`resolveEdgeInsets(tableHeadCellPadding, Density.defaultDensity.baseContentPadding)`)
   and also pins `tableCellPadding` the same way. The assertions are *stronger*: they
   still assert 8 horizontal / 0 vertical for the head cell and 8 all round for the
   body cell, and they now cover both constants.
2. **`layout_audit_density_test.dart` "select trigger: px-3 scales"** expected
   `(12 - 1) * scale`, i.e. it modelled the 1px trigger border as scaling with
   density. The border is a hairline the audit explicitly marks fixed
   (`border_hairline`, 3 sites) and `insetBorder` subtracts it after scaling, so the
   real value is `12 * scale - 1`. Replaced `expectScaled(horizontal: 11)` with a
   per-density `closeTo(12 * scaleAt(d) - 1, 0.001)` loop (plus a 0-vertical check
   and `expectMonotonic`). The assertion is now the correct model, and the reason is
   in the comment.
3. **`test/registry/components/chip_test.dart`** and **`badge_test.dart`** compared the
   rendered padding with the raw `chipDefaultPadding` / `badgeDefaultPadding`; those
   constants are now multipliers, so both compare against the resolved value.
4. **`test/registry/components/keyboard_shortcut_test.dart:322`** "the caps scale as a
   whole, **not** the padding" pinned `6x4` under `scaling: 2`. That is the opposite of
   the rule this brief mandates; the assertion now expects the resolved
   `EdgeInsets.symmetric(horizontal: 12, vertical: 8)` at `scaling: 2`, with a comment
   explaining that `AdaptiveScaling` scales radius/icons/typography in the same pass, so
   "scales as a whole" still holds.
5. **`test/registry/components/menubar_test.dart`** "default bar is 40 high: 32px row +
   p-1" still passes — the menubar's `style.padding ?? const EdgeInsets.all(4)` was
   replaced by a `resolveEdgeInsets` over `menubarDefaults.padding!`, which resolves
   to 4 at the default density.

### Harness fix (not a weakened assertion)

The dialog density test left its route mid-transition across pumps, and the resulting
focus-manager assertion ("Focused child does not have the same idea of its enclosing
scope") fired inside the *next* test (menu row) and failed the file. This is a
framework test-harness quirk, not a registry defect — the dialog behaves the same as
before. The test now pops the route and settles the transition before the next
density round; no assertion was removed or relaxed. Verified by reproducing it in
isolation (a scratch test was written, run, and removed; it is not committed).

## Open questions

1. `alertDefaults.gap` (12), `ChatTheme.spacing`/`avatarSpacing`,
   `SelectableRadioTheme.gap`, `treeDefaults.itemGap`, `phone_input`'s three gaps and
   `toastDefaults.gap` are `double` theme fields: a token reference cannot live in a
   const default of that type, so the values were kept and documented as
   `spacing.<step>` equivalents. A typed gap value (or making them
   `double Function(SpacingScale)`) would let them scale with the preset spacing base
   — that is a public API change and needs a decision.
2. `selectable_radio_theme.dart:236` (`EdgeInsets.all(2)`) and
   `window_host.dart:296` (`EdgeInsets.all(6)`) were off the padding grid's "nice"
   values. Both are ordinary `pxAll` cases (2/16, 6/16) which scale correctly; the
   consumers resolve them (the selectable radio row's padding reaches `roving_row`,
   and `window_host.dart` resolves its own).
3. `rearch/reports/P6-F1-primitives-BLOCKED.md` is a leftover from an aborted
   sub-agent attempt at the primitives batch. It contains explicitly unverified
   claims (notably on `selectable_radio_theme.dart`). It was **not** acted on; the
   primitives work in this report was done directly and verified against the code.
   Remove the stale file by hand.
4. The `-1` test in `flutter test test/registry/components` seen by one batch was
   `test/registry/components/sidebar_test.dart`, a file that does not exist (a batch's
   command listed it by mistake), not a failure.
5. **The scanner is blind to `const EdgeInsets.*` in a `padding:` argument it does not
   classify.** `spatial_scan_rules.dart` records `const EdgeInsets.all(24)` inside a
   `Padding` widget but not in any other constructor, so ~163 remaining
   `padding: const EdgeInsets.all(...)` sites in previews are invisible to the audit
   (roughly 73 gallery shells under `SingleChildScrollView(padding:)`, ~49 in-demo
   `Padding`, ~41 other). They are outside the audited 552 and were left alone, but a
   follow-up batch should first teach the scanner to record every `padding:` named
   argument, then convert.
