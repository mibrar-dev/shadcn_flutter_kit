# P6-F2 — theme-dependent colours + code selectability (report)

Unit: **P6-F2** · Date: 2026-10-10 · Scope: `$APP/lib/registry/**` (fix batch for P6-D9c)
Brief: `$KIT/rearch/briefs/P6-F2` (fix list in `$KIT/rearch/reports/P6_THEME_AUDIT.md` §4)

## 0. What was wrong

Two defects, both user-reported:

1. **Theme-dependent colours.** 19 scan findings classified `fix` in
   `rearch/reports/p6_theme_audit.json`, spread over 8 files. A component that
   declares its own literal palette cannot be restyled by a preset switch.
2. **Code not selectable.** `code_snippet` rendered plain `Text` / `Text.rich`
   with no selection container, so code blocks (including the docs "View Code"
   pane) could not be selected or copied.

## 1. Corrections to the audit's findings

The fix batch is where I verify the audit's claims against the code. Two of
them needed correcting, and one of them changes what "fix" means:

### 1.1 The white/black edge fades were not merely the wrong colour — they faded nothing

The audit (§1.2) reports the three edge-fade sites as "the gradient is white in
both modes; in dark mode it fades to light". **That diagnosis is wrong, and the
bug is worse.** `ShaderMaskLayer` composites the shader *over* the child with the
configured blend mode (`$FLUTTER/engine/src/flutter/flow/layers/shader_mask_layer.cc`,
`Paint()` → `saveLayer` + `DrawRect` with `dl_paint.setBlendMode`), and
`BlendMode.modulate` multiplies **colour only**:

> `dart:ui` `BlendMode.modulate` — "Multiply the color components of the source
> and destination images… For a variant that also multiplies the alpha channel,
> consider `multiply`."
> — `$FLUTTER/engine/src/flutter/lib/ui/painting.dart:748-773`

The old gradients were `[Color(0x00FFFFFF), white, white, Color(0x00FFFFFF)]`
(`overflow_marquee.dart:355-358`, `number_ticker.dart:323-326`) — transparent
**white**. Under `modulate` the alpha 0 endpoints multiply colour by white
(identity) and leave the destination alpha untouched, so **the mask was a
complete no-op**: content never faded at either edge, in either brightness.
`Color(0x00FFFFFF)` reads like "transparent" but only `dstIn` / `multiply` /
`srcIn` consume source alpha.

So the fix is not "resolve the colour from `background`" — it is **switch the
blend mode to `BlendMode.dstIn`** and fade toward the surface token. `dstIn`
keeps the destination wherever the source is opaque and clears it where the
source is transparent, which is what a `modulate`-with-white mask *looks* like
it does. `scrollable.dart:150-153` already used `dstIn` (correctly) but with a
hard black `0xFF000000` mid-stop; for `dstIn` the RGB is irrelevant, so that one
was cosmetic and is now token-driven anyway.

### 1.2 `gooey_toast`'s 6 tones: mapping chosen

shadcn has no success/loading/warning/info/action token. The audit asked for
"chart1..chart5, destructive, mutedForeground as proposed" but left the exact
pairing open. Chosen mapping (documented in `gooeyToastDefaults`):

| state | token | why |
|---|---|---|
| success | `chart1` | categorical "good" hue |
| loading | `mutedForeground` | neutral, low-emphasis activity |
| error | `destructive` | shadcn's own error token |
| warning | `chart4` | amber slot of the categorical scale |
| info | `chart2` | cool/blue slot |
| action | `chart5` | violet slot for interactive affordances |

### 1.3 `tracker` fine / warning: mapped, and why literals were wrong here

The audit left this "jury out" (its open question 1) and noted that keeping
`0xFF22C55E` / `0xFFF59E0B` is "arguably semantic". I mapped them:

- `fine` → `ColorRef.chart2`
- `warning` → `ColorRef.chart4`

Rationale, from the chart scales of the three audited presets: in `neutral`,
`claude` and `tangerine` the `chart1..5` ordering is a perceptual ramp from
green through amber to violet, so `chart2` *is* the green/teal slot and
`chart4` the amber slot. The literal green/amber then restyles with the preset
instead of staying fixed, which is the user's requirement ("every component
follows the selected theme live"). Same row already applied for `critical`
(`destructive`) and `unknown` (`mutedForeground`).

### 2.2 Code selectability (audit §3 option A)

`components/code_snippet/code_snippet.dart` wraps `_codeChild(ambient)` in

```dart
SelectableRegion(
  selectionControls: ShadcnSelectionControls(),
  child: _codeChild(ambient),
)
```

`Text` and `Text.rich` register with the nearest `SelectionContainer`
automatically (`$FLUTTER/packages/flutter/lib/src/widgets/text.dart:745` and
`:964` both read `SelectionContainer.maybeOf(context)` and pass the registrar to
`RichText`), so per-token syntax colours are untouched and only selection/copy
is added. `SelectableText` was deliberately not used (audit option B): it would
need a per-instance focus node and would misbehave inside a caller's
`SelectionArea`.

`markdown` fenced code needed **no change** — it already wraps in
`SelectableRegion` and forwards `selectionRegistrar`
(`markdown_parser/blocks.dart:74-88`, `markdown.dart:279-286`); the test now
covers it.

Coverage notes a reviewer will want:
- the marquee's mask is asserted through `RenderObject.debugLayer` (a `ShaderMaskLayer`
  is the only place the blend mode is observable — a shader is opaque to the
  widget tree);
- the ticker's mask only exists mid-roll, so the test rolls one digit to the
  next under `FlipperCharset.numbers` (integer indices ⇒ a fractional value for
  half the run);
- the clipboard is asserted through a `TestDefaultBinaryMessenger` handler,
  because `Clipboard.getData` has no platform handler in `flutter_test` and
  never resolves;
- the keyboard path is covered by invoking the same intents `Ctrl/Cmd+A` and
  `Ctrl/Cmd+C` dispatch; a mouse-drag path was tried and dropped (it hangs in
  `flutter_test` without a real pointer device).

## 5. Open questions for the QA lead

1. **The audit's edge-fade diagnosis was wrong** (§1.1) and `rearch/reports/
   P6_THEME_AUDIT.md` §1.2 should be corrected: those sites did not "fade toward
   a light colour", they did not fade at all. Any other site using
   `BlendMode.modulate` with alpha-bearing stops has the same latent bug — I
   found none, but the pattern is worth a repo-wide grep.
2. **`chart2` / `chart4` as green / amber** — inferred from the three presets'
   chart ramps, not from a shadcn spec. If the design owner disagrees, note that
   `fine` / `warning` are `ThemedColor` fields, so only the two defaults change.
3. **`descriptionColor` is a new `GooeyToastTheme` field** — the minimal way to
   keep the description token-driven and Studio-editable, since a `const
   TextStyle` cannot hold a `ThemedColor`. It is a natural addition to a
   nullable-field theme class (no API break), but it is a new public surface.
4. **`SelectableRegion` needs an `Overlay` ancestor.** Any caller that renders
   `CodeSnippet` without one now trips a framework assert. The component test
   harness needed `_OverlayHost`; the docs pages render through the component
   and already have an `Overlay`. A future builder or a bare `MaterialApp`-free
   test would need the same treatment.
5. **Docs "View Code" pane** — `docs/**` is another unit's scope. If those
   surfaces render the registry `CodeSnippet` (they appear to, via
   `generated/docs_snippets.dart`), they are covered by this fix; if they build
   their own code widget they still need the selectability pass.
