## 1. Forgot-password trailing links (brief §1)

Root cause confirmed from code (not the old claim alone): the rows used
`Spacer` + loose `Flexible(Text, end)`. A loose `Flexible` sizes the `Text`
to its content and start-aligns it inside its allocation, so the text's right
edge stops short of the row (and the static `Text` had no handler). The link
`Button` defaults additionally carried the `md` size-table padding (16 px
horizontal), which would inset any link text by the same amount.

Fix:

- `components/button/button_style.dart`: `link` and `text` baseline rows now
  carry `padding: EdgeInsets.zero` — shadcn links are plain `ml-auto`
  anchors with no horizontal padding. (Pilot metrics tests only assert
  sm/md/lg primary padding, so they are unaffected.)
- `login-01`: the `Password` label keeps its natural width; the link side is
  `Expanded` + `Align.centerRight` + `Button(variant: link)` (never a loose
  `Flexible`). The `Text` wraps (`softWrap`, `end`) instead of overflowing in
  the Ahem test font, and wrapped lines stay end-aligned.
- `login-03` forgot row: same pattern without a label
  (`Expanded` + right-aligned link button).
- `login-02`: verified it carries no forgot row (checked, no change).
- Footers that were plain handler-less text are now static text plus a real
  link button: login-03 `Sign up`, signup-02 `Sign in`, otp-01
  `Use a different email`. Signup-01/02 terms sentences use inline link
  buttons for `terms` / `privacy policy` (were dead underlined spans / static
  text). All demo links use `onPressed: () {}` so they render enabled.
- `otp-01` `Resend` was already a link button and inherits the zero padding;
  the visible countdown state is covered by alignment too.

Tests (`blocks_polish_test`, 5 old + 8 new = 13, all pass): link/text
defaults equal `EdgeInsets.zero`; login-01/03 forgot text right == password
field right (|Δ| < 1.5 px) at **both** 375 and 1440; login-02 has no `Forgot`
row; auth footers resolve to enabled link buttons; otp-01 `Resend in 47s`
right == `Verify` action right (|Δ| < 1.5 px).

## 2. Docs block viewport, one continuous card (brief §2)

Diagnosis with a probe test (rects/colours, no images): the outer card
`DecoratedBox` (radiusXl + border) already wrapped header + tabs + viewport,
but the desktop viewport painted a *second* inner bordered box on a 16 px
padded inset — a double frame, and the 1 px inner border on the same
background read as no frame under the tab row.

Fix (`docs/lib/widgets/block_viewport.dart`): desktop (`viewport.width ==
null`) now fills the card edge to edge with background fill only — no inner
padding, no inner border — so the card's own border is the single continuous
frame for header + tabs + viewport (shadcn `/blocks`). Tablet/mobile keep
their centred bordered device frame. Heights unchanged.

Test rewrite (`docs/test/blocks_pages_test.dart`): the P6-P3 test passed on
header text + frame key even when the visible border stopped at the tab row.
It now finds the `DecoratedBox` border that actually paints and asserts its
rect contains BOTH the tab row (`Preview` text center) and the block content
(`Forgot password?` center) on `/blocks/login-01`, asserts exactly one such
painter, and asserts the winner's top/bottom equal the card's (it is the card
itself, not an inner frame). The desktop-width expectation is updated
accordingly (frame == card width, not card − 32). The background-token test
still passes (desktop frame keeps the background fill, borderless).

bordered `Container` + raw `'<'` / `'>'` glyph for the registry control:

  variant: ButtonVariant.ghost,
  size: ButtonSize.icon,
  onPressed: onPressed,
  child: Icon(icon, size: 16), // chevronLeft / chevronRight

`foundation/icons` import added; `blocks/calendar-0{1,2}/meta.json` foundation
gains `icons`; `registry.json` regened; generated `blocks_meta_test`
derived-deps regened (`gen_blocks_test.dart`, `--check` clean). Tests assert
one `chevronLeft` + one `chevronRight` icon per block, each inside an enabled
ghost icon-size `Button`, and `find.text('<')` / `find.text('>')` are empty.

## 4. Home / themes / block scan (brief §4)

- Home collage (`collage_home_*`, `collage_cards_*`): every demo control
  carries a handler (`collageNoop` / `() {}` / local state setters); no text
  glyph used as an icon found.
- `/themes` (rail + canvas): every picker/reset/brightness control wires
  `onChanged`/`onPressed` through the studio model; no dead controls found.
- Blocks: `blocks_interactive_test` (18) still green — no disabled demo
  control outside the whitelisted calendar-02 taken slots.
- Fixed: `scaffold/preview.dart` used `Text('<')` / `Text('...')` as bar
  glyphs → `Icon(chevronLeft)` / `Icon(ellipsis)`; `context_menu/preview.dart`
  submenu chevron `Text('>')` → `Icon(chevronRight)`. Preview-only imports, so
  no installed-deps change (previews are excluded from meta deps).
- Left deliberately: `calendar/preview.dart` still uses `'<'`/`'>'` demo
  steppers — component scope (changing them to `Button` icon would add a
  `button` dep to `calendar` and break the pinned 24×24 stepper test);
  flagged as a component-owner follow-up, same class as the P6-P2 open
  question.
